# Architecture Decision Records (ADRs)
**Portfolio Immortalized — Pie Corp Limited**
**Baseline Date:** October 2026
**Status:** Approved Baseline (TDD v1.0)

---

## ADR-001: Mobile and Web Client Stack
- **Status:** Approved Baseline
- **Context:** The platform requires a mobile-first user experience for account holders (document scanning, video recording, biometric app unlock, upload recovery) alongside responsive web interfaces for owners, trustees, beneficiaries, and administrators.
- **Decision:** Use **TypeScript** throughout. **Next.js (App Router)** with **Tailwind CSS** and **GSAP** for the responsive web application and portals; **React Native with Expo** and **React Native Reanimated** for the mobile application (iOS & Android).
- **Consequences:** Maximizes code and type sharing across web and mobile via shared monorepo packages (`packages/domain`, `packages/validation`, `packages/api-client`).

---

## ADR-002: Backend and Data-Access Shape
- **Status:** Approved Baseline
- **Context:** Need a maintainable, secure backend service architecture without premature microservice sprawl, ensuring consistent server-side authorization on all operations.
- **Decision:** Implement server-side domain services, a centralized Data Access Layer (DAL), and API Route Handlers in Next.js for the first release, with an optional separate TypeScript background worker for heavy asynchronous jobs (scheduled sweeps, media processing, outbox publishing).
- **Consequences:** Eliminates client-side database calls; enforces all reads and writes through server-authoritative ownership and policy checks.

---

## ADR-003: Database and ORM
- **Status:** Approved Baseline
- **Context:** The legacy lifecycle requires relational integrity for multi-party relationships, legal holds, audit trails, and death case state transitions.
- **Decision:** Use **PostgreSQL on Supabase** accessed strictly via **Prisma ORM** from trusted server-side code. All migrations must be version-controlled and applied via `prisma migrate deploy`.
- **Consequences:** Direct client access using Supabase service-role keys is strictly prohibited. Referential actions for critical tables default to `RESTRICT` to prevent accidental cascading deletion.

---

## ADR-004: Authentication and Session Policy
- **Status:** Approved Baseline
- **Context:** Digital legacy custody requires strong identity verification, phishing-resistant credentials, and action-bound step-up authentication.
- **Decision:** Integrate **Better Auth** with server-managed sessions. Web clients use `Secure`, `HttpOnly`, `SameSite=Lax/Strict` cookies; mobile clients store session credentials in **Expo SecureStore** (iOS Keychain / Android Keystore). Email OTP and passkeys are supported.
- **Consequences:** Bearer tokens are never exposed in `localStorage`. Step-up authentication is mandatory for sensitive actions (changing beneficiaries, modifying recovery channels, final release approval).

## ADR-005: Asset Envelope Encryption
- **Status:** Approved Baseline
- **Context:** Wills, identity records, and personal media demand the highest confidentiality. However, beneficiaries must be able to access specifically authorized assets after verified death without a single-insider bypass.
- **Decision:** Adopt an **Envelope Encryption** model using AEAD (**AES-256-GCM** with 96-bit unique nonces or ChaCha20-Poly1305). Each asset version receives a fresh, cryptographically random Data Encryption Key (DEK). The DEK is encrypted with a Key Encryption Key (KEK) managed in an approved KMS/HSM service.
- **Consequences:** Plaintext DEKs only exist ephemerally in server memory during authorized crypto operations and are never written to the database, returned to clients, or logged.

## ADR-006: Death Verification and Controlled Release Model
- **Status:** Approved Baseline
- **Context:** Critical safety risk of false death declarations and accidental asset disclosure.
- **Decision:** 
  1. Inactivity is an escalation signal, never proof of death. No manual "I Am Alive" button.
  2. Suspected death triggers an investigation case, not automatic release.
  3. Every release grant requires a verified death case, trustee evidence, policy checks, and **two-person independent administrator authorization** (Case Reviewer != Final Approver).
  4. An emergency hold can be placed immediately by any authorized security actor or verified owner response.
- **Consequences:** Zero automated timer-based releases. Fails closed on any evidence ambiguity.

## ADR-007: Administrator Roles and Separation of Duties
- **Status:** Approved Baseline
- **Context:** Insider threats, phished credentials, or single points of failure in administrative oversight.
- **Decision:** Named individual administrator accounts with Role-Based Access Control (RBAC) and explicit permission scopes (`users.read`, `cases.review`, `releases.approve`, `security.incident.manage`). Shared super-admin logins are banned.
- **Consequences:** Strict separation of duties: the administrator reviewing case evidence cannot issue the final release approval for the same case. All admin actions are written to an append-only audit log.

---

## ADR-008: Storage Provider Architecture
- **Status:** Approved Baseline
- **Context:** Secure storage of legal documents, multi-page PDF scans, family videos, and audio notes.
- **Decision:** Private object storage (e.g. Supabase Storage / S3-compatible) with server-brokered or short-lived signed access for confidential assets (Class C3/C4). Cloudinary is permitted only for approved non-sensitive public assets (Class C0).
- **Consequences:** Confidential files are encrypted prior to storage; bucket paths use random UUIDs and are never used as access-control mechanisms.

---

## ADR-009: Provider-Neutral AI Gateway
- **Status:** Approved Baseline
- **Context:** AI assistance provides value for user onboarding, scan blur detection, and draft case summaries, but presents risks of prompt injection, data leakage, and unauthorized agency.
- **Decision:** Route all AI operations through an internal **AI Gateway** with support for Gemini and Claude adapters. Restrict AI to low-risk tasks behind an explicit task allowlist.
- **Consequences:** **AI has zero authority over release, death verification, or account deletion.** Models receive minimized PII and run with temperature controls and JSON-schema output enforcement.

---

## ADR-010: Append-Only Transactional Audit Logging
- **Status:** Approved Baseline
- **Context:** Complete accountability and tamper-evident history are mandatory for legal compliance and security investigations.
- **Decision:** Implement a transactional `AuditEvent` table recording actor, target, action, outcome, timestamp, and request/trace ID. All critical state transitions commit the domain mutation and audit event in a single database transaction.
- **Consequences:** Direct UPDATE and DELETE operations on audit records are blocked. Outbox events are written transactionally to publish notifications and background jobs reliably.
